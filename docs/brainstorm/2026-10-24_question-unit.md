# 2026-10-24 作業フローマップのタスクを「問い」の単位にする

- 参加者：
- 状態：議論中

## 今回の問い

研究を進めると小さな問いがいくつも出てきて、それを順に解いていく。今の TAZUNA は、プロジェクト（研究テーマ）1つに研究の目的が1組あるだけで、判定（F-4〜F-6）と先生モード（F-8）はその大きな目的にしか照らしていない。問いごとに「実装が合っているか」と「理解できているか」を確かめるには、どう作ればよいか。デモ（Day2 15:00 Code Freeze）までにどこまでやるか。

## 今の作り

- プロジェクト = 研究テーマ1つ = GitHub のリポジトリ1つ。研究の目的（問い・手法・評価）は1組（F-1）
- 判定は、変更を「研究の目的」と「作業の目的（依頼文）」に照らして分ける（`ReviewRequest` の `theme` と `purpose`）
- 先生モードは、プロジェクトに保存した問題すべてと、研究の目的について質問する（`TeacherQuestionsRequest` の `theme` と `problems`）
- 作業フローマップ（F-15）には、研究の中の小さな問いがタスクとして並び、タスクごとに目的（`purpose`）と状態がある。判定を保存するとマップを自動で更新し、変更をタスクに結び付ける（`MapTask.reviewIds`、`link_task`）
- ただし、その結び付きを判定にも先生モードにも使っていない。判定のときにはまだどのタスクの変更か決まっておらず、先生モードはタスクを見ない
- 最初の壁打ち（[テーマ決め](2026-10-24_theme.md)）の「問いのアンカー」（今の問いと工程を宣言して常に出す）は、F-11（Could）のまま実装していない。「今ここ」「今の段階」（F-15）が工程の側だけを受け持っている

## 出たアイデア・意見

### 問いの単位は作業フローマップのタスクにする

- 新しく「問い」を作らず、マップの **親を持たないタスク** を問いの単位として使う。タスクにはもう目的・状態・出典（spec や実験記録）があり、今ここ・今の段階ともつながる
- サブタスクは細かすぎるので、まずは単位にしない（後で考える）

### 取り組む問いを宣言する（問いのアンカー）

- 「今ここ」（直近の更新・新しい記録から自動で選ぶ）を、そのまま判定に使う問いにすると、ずれることがある。デモでは取り込み前の今ここが「seed 3 つで linear と cosine を比較する（比較スクリプト待ち）」だが、Claude Code に頼む作業は実装の「cosine スケジュールと比較スクリプト」
- そこで、学生がマップ（S-7 のタスクの詳細と帯）で **「この問いに取り組む」** と宣言できるようにする。宣言した問いはマップに覚えておき（例：`WorkflowMap.activeTaskId`）、帯と S-7 の今ここの囲みに「取り組み中の問い」として出す。宣言を外すこともできる
- 今ここの決め方の先頭に「宣言した問い」を足す：① 宣言した問い ② 直近の更新で変わったタスク ③ 記録の日付が新しいもの ④ 工程の順
- 研究の工程のどこにいるか（今の段階）と、今どの問いを解いているか（取り組み中の問い）が1か所で分かるようになる

### 判定を問いごとにする

- 判定のときに、取り組み中の問い（無ければ今ここ）を決めて、判定に添える。保存する判定に `taskId` と、そのときのタスクの題名・目的の写しを残す（タスクはあとで直したり消したりできるため）
  - フック（F-13）：届いたときの取り組み中の問いを自動で付ける。学生は何もしなくてよい
  - コミットから取り込む（S-2）：問いを選ぶ欄を置き、取り組み中の問いを初期値にする
- AI に渡すもの：今までの研究の目的と依頼文に、問いの題名と目的を足す（プロンプトに `<question_task>` のような欄を足す）
  - 「目的どおり」かは、依頼文と問いの目的で見る
  - 「研究への影響」は、今までどおり研究の目的（例：元のスケールで測る、変えるのはスケジュールだけ）で見る。問いの目的が研究の目的とぶつかるときも、研究の目的を優先する
- S-3 に「問い：〈タスク名〉」を出し、S-7 のそのタスクへ飛べるようにする。違う問いだったときは、問いを変えて判定し直せる（今の「目的を直して判定し直す」を広げる）
- マップの自動更新では、判定の `taskId` のタスクにその変更を必ず結び付ける（AI に任せず、決まった `link_task` を先に当てる）。AI の更新はそのあと
- API 呼び出しは増えない。プロンプトが少し長くなるだけ

### 先生モードを問いごとにする

- S-7 のタスクの詳細と、帯の今ここの囲みに **「この問いで先生モード」** を置く。開くと `/themes/[themeId]/teacher?task=<id>` になる
- 質問に使うもの：そのタスクに結び付いた判定（`taskId` が同じもの、または `reviewIds` にあるもの）で保存した問題と、タスクの題名・目的。研究の目的も今までどおり渡す
- 保存した問題が無い問いでも、研究手法の層（「なぜこの評価指標？」など）はタスクの目的と出典から聞ける
- 先生モードの記録（`TeacherSession`）に `taskId` を残し、「答えられなかった点」を問いごとに見返せるようにする。マップのタスクの詳細にも出す
- プロジェクト全体の先生モード（今のもの）は、ゼミ前の総復習として残す
- もとの③「手法上の問いの立て方」（未決事項）は、この「問いごとの先生モード」の研究手法の層の聞き方として扱える

### 問題ログ

- 保存した問題に、どの問いのときのものかを出す。問いで絞り込めるようにする

## 却下した案とその理由

- **「問い」を新しいデータとして別に作る**：マップのタスクと二重になり、どちらも直す手間が出る。タスクには目的・状態・出典がもうある
- **問いごとにプロジェクトを分ける**：リポジトリが同じプロジェクトが増え、研究の目的がばらばらになる。フックは「リポジトリ1つにプロジェクト1つ」で届け先を決めているので、届け先も決められなくなる
- **今ここをそのまま判定に使う問いにする**：デモの例のように、自動で選んだ今ここと、実際に頼んだ作業の問いがずれる。宣言を優先し、今ここは宣言が無いときの初期値にする
- **どの問いの変更かを AI に毎回当てさせる**：呼び出しが増え、外れたときに判定の基準ごとずれる。まずは人の宣言と初期値で決め、違ったら直せるようにする
- **サブタスクまで問いの単位にする**：細かすぎて宣言が手間になる

## デモまでにやる範囲（Day2 15:00 Code Freeze まで）

デモで見せるのは「問いを宣言 → Claude Code に頼む → 問いに照らした判定 → その問いで先生モード」の1本だけに絞る。

| 順 | やること | 担当 | 目安 |
| --- | --- | --- | --- |
| 0 | 共通の型を入れる（`Review.taskId` と問いの写し、`TeacherSession.taskId`、`WorkflowMap.activeTaskId`。省略可） | ① | 30分 |
| 1 | 「この問いに取り組む」の宣言と、今ここの決め方の先頭に宣言を足す（S-7 のタスクの詳細、帯と S-7 の今ここの囲みに「取り組み中の問い」） | ③ | 2時間 |
| 2 | 判定に問いを添える（フックは取り組み中の問いを自動で、S-2 は選ぶ欄。プロンプトに問いの欄。S-3 に「問い：〈タスク名〉」） | ① | 2〜3時間 |
| 3 | 自動更新で判定の `taskId` のタスクに必ず結び付ける | ③ | 1時間 |
| 4 | 問いごとの先生モード（S-7 のタスクの詳細に「この問いで先生モード」、`?task=` で問題と問いの目的を絞って質問、記録に `taskId`） | ② | 2〜3時間 |
| 5 | デモデータとデモの手順を合わせる（デモの判定に問いを付ける、宣言する場面を台本に入れる）、設計書・使い方ページ | ① と ③ | 1時間 |

デモの後（README の「今後の展望」に書く）：

- S-3 で問いを変えて判定し直す
- 問題ログを問いで絞り込む
- 問いごとの「答えられなかった点」をマップのタスクに出し、理解できていない問いが一目で分かるようにする
- サブタスクを問いの単位にするか
- どの問いの変更かを AI が提案する
