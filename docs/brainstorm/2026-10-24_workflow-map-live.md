# 2026-10-24 作業フローマップをデモモード以外でも使う

- 参加者：
- 状態：結論あり（設計書に反映済み）

## 今回の問い

デモデータだけで動いている作業フローマップ（F-15）を、本物の research-workspace と実装リポジトリから作り、更新できるようにするには、何を決めればよいか。

## 出たアイデア・意見

- 作り方は「AI なしで記録だけ」「記録＋AI」の2案。記録だけなら無料で速く、AI の間違いも入らない。AI を足すと、目的の要約・まとまり・不採用の案が出せる
- research-workspace は frontmatter でファイル同士がつながっているので、骨格（flow と状態）は AI なしで作れる
- LLM は設計書どおり Claude Haiku 5.5。生成1回が1〜2円程度、更新は1円未満の見込み
- ワークスペースの指定を毎回聞くのは手間。1回だけ聞いて覚えておく。置き場所はプロジェクト（`ResearchTheme`）かマップ。プロジェクトの型は新しいプロジェクトの画面（S-6）と共有しているので、マップに置けばほかの担当に触れずに済む
- 自動更新を S-3 を開いたときに走らせると、フックで次々に届く判定のうち開かなかったものが反映されない
- ワークスペースだけ更新されたとき（実装の取り込みが無いとき）は、自動では拾えない

## 却下した案とその理由

- **AI なしで記録だけで作る（案1）**：目的やまとまりが出ないので、記録＋AI（案2）にした。ただし API キーが無いときは記録だけで作る
- **ワークスペースの指定をプロジェクトに保存する**：今はマップ以外に使う機能が無く、プロジェクトの型を変えるとほかの担当との調整が要るため、マップに保存した
- **作り直しでマップを丸ごと置き換える**：人の手直しと却下したものが消えるため、自動更新と同じ当てはめにした
- **S-3 を開いたときに自動更新する**：開かなかった判定が反映されないため、判定を保存したときにした

## 決まったこと

- ワークスペースの指定：S-7 で最初にマップを作るときに1回だけ入力し、マップに保存する。以後は聞かない。設定から変えられる
- 読む形式：まず research-workspace の形式だけ
- 読む範囲：プロジェクトの README・specs・experiments・meetings・materials・papers と、`project:` が一致する壁打ち。`code-analysis/` と画像は読まない。最大約200件、新しい順
- 作り方：frontmatter のリンクで骨格を作り（AI なし）、Claude Haiku 5.5 が目的の要約・まとまり・不採用の案・研究への影響の矢印を補う。人の手直しもできる
- 作り直し：自動更新と同じ当てはめ（人の手直しと却下したものを守る）
- 自動更新：判定を保存したとき（S-2 の取り込み、フックの受け取り箱）に走らせる。S-3 は結果を見せるだけ
- 読み方：前回から変わったファイルだけ読む
- ワークスペースだけ更新されたとき：S-7 の「ワークスペースから更新」ボタンで更新する
- AI に送ることを画面に出す。状態の優先順位（手動 ＞ 記録 ＞ AI推測）、取り消しで人の手直しが消えない、用語（研究テーマ → プロジェクト）も直す
- 作業はブランチ `feature/workflow-map-live`
