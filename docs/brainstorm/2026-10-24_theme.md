# 2026-10-24 テーマ決め：生成AI時代の研究の悩み

- 参加者：
- 状態：結論あり（設計書の初版に反映済み）

## 今回の問い

何をテーマにし、どの悩みを解決するプロダクトにするか。

## 決まったこと

- テーマは **「生成AI時代の研究の悩み解決」**
- 悩みは①〜⑩の10個で全部（⑪以降はない）
- 想定ユーザーは **情報系の研究室** の学生に絞る
- 解決する悩みは **グループA（① ③ ④）＋グループC（⑥ ⑧）** で進める。余裕があればグループB（② ⑤ ⑦ ⑨ ⑩）にも取り組む
- 使い方の形は **Web アプリ**
- チームは **3人**。特に得意分野はない
- AIが書いたコードの変更は **GitHub 連携** で受け取る
- ⑧ 専用の機能（実装前チェック）は作らない。目的の明確化と差分の照合で対応する
- 「隠れた問題」として保存するのは **エラー内容とその対処方法**
- 保存した問題は **自分で見返せればよい**（共有機能はいらない）
- ずれが「本当に問題があった」のか「AIの余計な追加」なのかは **AIが判定する**
- **目的と理解は「実装」だけでなく「研究手法」の両方を扱う**。研究手法についても、目的や理解が追いつかない問題がある。目的を書くときも、先生モードでも、研究手法の話を忘れない
- **今の形で設計書の初版を作り、実際に動くアプリを見ながら修正していく**。未決の部分は設計書で【仮】として埋める

## 解決したい悩み（現在の企画）

| # | 悩み |
| --- | --- |
| ① | 研究の進むスピードが速すぎて、それを理解できない自分がボトルネックになっている |
| ② | 情報量が多すぎて、探索フェーズが終わらない |
| ③ | 自分が意図していない実装になっていても気づかない |
| ④ | 先生に「ここどうなっている？」と聞かれて、理解できていないことが露呈する |
| ⑤ | 壁打ちが不足していると、実装の目的を把握できていない |
| ⑥ | エラーを修正するときに、AIが勝手に機能を付け足して、認知負荷が上がる |
| ⑦ | いろいろな情報を深掘りできてしまうため、いつの間にか方針を見失う |
| ⑧ | すぐ実装したがり、いつの間にか実装してしまう |
| ⑨ | ちょっとした成功・失敗に一喜一憂して、方針からずれていく |
| ⑩ | 自分の立ち位置を見失う。具体的には、**今の作業の問いが何だったかを忘れる**ことと、**研究の工程のどこにいるか分からなくなる**こと |

## 出たアイデア・意見

### 悩みの整理（3グループ）

| グループ | 悩み | 根っこ |
| --- | --- | --- |
| A. 理解が追いつかない | ① ③ ④ | AIが作る速さに、人間の理解が追いついていない |
| B. 問いと現在地を見失う | ② ⑤ ⑦ ⑨ ⑩ | 「今なにを明らかにしたいのか」を持ち続けられない |
| C. AIと自分の暴走 | ⑥ ⑧ | 目的の外に手が動いてしまう（AIも自分も） |

共通する根っこ：ボトルネックが「作ること」から「理解すること」と「舵を取ること」に移った。今のAIツールはアクセル（速く作る）ばかりで、**ハンドルとブレーキ**を担うものがない。

### プロダクトの骨格（たたき台）

研究者とコーディングAIの間に入り、問いを固定し、理解を確かめるツール。

1. **問いのアンカー**（B）— 作業開始時に「今の問い」と「工程」（探索／仮説／実装／検証／まとめ）を宣言して常に表示。外れたら知らせる。探索にタイムボックス（②）
2. **意図と差分の照合**（③ ⑥）— AIの変更差分を宣言した意図と照らし合わせ、頼んでいない機能追加や意図と違う実装を検知
3. **先生モード**（① ④）— マージ前にAIが先生役で「ここどうなってる？」と質問。答えられなかった箇所を記録
4. **工程ゲート**（⑤ ⑧）— 壁打ちが済んでいないと実装の工程に進めない

### 懸念

- 10個全部は14時間弱では無理。デモが中途半端になる
- おすすめは「問いのアンカー」＋「意図と差分の照合」＋「先生モード」を一本のフローにすること。デモは「AIが勝手に機能を足す → 検知 → 先生モードで答えられない → 記録」の流れ
- 論文を読む側の悩み（① ② ⑦）は NotebookLM・Elicit などと被りやすく、差別化しにくい
- 名古屋会場のスポンサー賞とは相性が弱め（強いて言えば Acompany の「AI活用に信頼を」）。Award Day 進出が本命
- 大会テーマの「縦方向のフルスタック」は「研究の問いから実装まで人間が舵を握る」で説明できる。物理デバイス（今の問いと工程を示す卓上デバイス）は任意
- 審査員の多くは大学の先生なので、④は課題として強く共感されやすい

### 意図とずれた実装は「隠れた問題」のサイン（ユーザーの発案）

- AIが自分の思っていた目的と違う実装をしたときは、**何かしらの問題があって、それをAIが勝手に解決した**ということ
- その「問題」はどこかに保存しておきたい
- 壁打ちでの補足：
  - ずれは「AIのミス」とは限らない。**自分が知らなかった問題を見つける手がかり**になる。⑥の「勝手な付け足し」を、ただ消すだけでなく学びに変えられる
  - ただし、ずれには少なくとも2種類ある。①本当に問題があり、AIがそれに対処した場合（記録して理解すべき） ②問題はなく、AIが余計なことをした場合（取り消すべき）。この見分けが必要
  - 保存した問題がたまれば、先生に「ここどうなっている？」と聞かれたときの答えになる（④）。研究の実装上のハマりどころの記録として、論文を書くときや後輩への引き継ぎにも使える

### 研究手法の層も扱う（ユーザーの指摘）

- 議論が実装の話に偏っていた。研究手法についても「目的が曖昧」「理解が追いつかない」問題がある
- 壁打ちでの提案（未決）：
  - **目的は2層で書く**：研究の層（何を明らかにしたいか・どの手法で・どう評価するか）は研究テーマごとに1回、実装の層（今回AIに何を作らせるか）は作業ごとに書く。実装の目的が研究のどこにつながるかを示す
  - **先生モードも2層で質問する**：実装の質問（「この関数は何をしている？」）に加えて、研究手法の質問（「なぜこの手法を選んだ？」「ベースラインは？」「この評価指標で何が言える？」「先行研究との違いは？」）
  - **隠れた問題に「研究への影響」を付ける**：AIの対処が実験条件や結果を変えていないかを示す。例：欠損値のある行をAIが黙って除外した → データセットが変わり、実験の妥当性に影響する。汎用のコーディングツールにはない、研究ならではの観点

## 却下した案とその理由

- **実装前チェック（⑧への対策）**：目的を明確にしておけば、AIのコード変更を受け取って照合する段階で⑧にも対応できるため、専用の機能はいったん作らない
