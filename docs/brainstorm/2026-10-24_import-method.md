# 2026-10-24 AI の変更の取り込み方

- 参加者：Yuki Ogata（①の担当）、Claude Code
- 状態：結論あり

## 今回の問い

AI が変更したコードを、どうやってアプリに取り込んで判定するか。今の実装（GitHub に push したコミットを選んで取り込む）のままでよいか。

## 出たアイデア・意見

- **push 後に取り込む（今の実装）**：もうできていて、学生の PC に何も入れなくてよい。ただし push するまで判定できず、コミット・push・コミットの選択という手間がある。1コミットずつしか見られない
- **Claude Code のフック**：AI が作業を終えた時点で、未コミットの変更を自動で判定に回す
  - `UserPromptSubmit` フックで学生の依頼文を受け取れるので、それをそのまま作業の目的にできる
  - フックには会話記録（transcript）の場所が渡される。会話記録には、AI が実行したコマンドとその出力（失敗したものは `is_error`）が残っているので、**隠れた問題のエラー内容を推測ではなく事実で取れる**。このアプリの中心の価値に直結する
  - Claude Code 専用になる
- **差分の貼り付け**：`git diff` の結果を画面に貼る。一番軽いが手作業
- **Git のフック（post-commit など）**：どの AI ツールでも使える。ただし、目的はコミットメッセージ（AI が書くことが多い）になり、起きたエラーは Git に残らないので推測になる。AI 以外のコミットも混ざる
- **GitHub Actions**：push や PR のたびに判定して PR にコメントする。結果がアプリの問題ログに入らない
- **Claude Code のスキル**：Claude Code 自身に判定させる。サーバーも API キーも要らないが、自分の変更を自分で判定するので甘くなりやすい
- **アプリが AI を動かす**：判定は最も正確になるが、AI コーディングツールを作ることになる。ハッカソンでは無理
- **費用**：判定1回は Opus 5.5 で数十円、Haiku 5.5 なら約1円。フック方式は回数が増えるので、モデルは Haiku 5.5 にした（設計書に反映済み）。差分がない回は送らないことで、回数を抑える

## 却下した案とその理由

- **判定結果をデータベースに保存して、公開したアプリで見る**：データベース・認証・保存の作り直しで作業量が大きい。ハッカソンの期間では重い
- **判定結果を Claude Code の画面に出すだけ**：問題ログへの保存や先生モードにつながらない
- **Git のフック**：コストを度外視しても、目的とエラー内容の正確さで Claude Code のフックに劣る。「どの AI でも使える」広さは、今後の展望として残す

## 決まったこと

- 取り込みの主な方法を **Claude Code のフック** にする
- フックは、**手元で動かしているアプリ（localhost）** に変更を送る。ブラウザの画面がそれを受け取って判定し、今の localStorage に保存する。データベースは使わない
- **会話記録から、実際に起きたエラーを取り出して判定に使う**
- 今の「push 後にコミットを選んで取り込む」画面（S-2）は **残す**。フックを入れていない人、過去のコミットの判定、デモの予備に使う

## フック方式の問題点の洗い出し（設計を書いたあと）

- 「続けて」「エラー直して」のような短い依頼が作業の目的になり、判定が意味をなさない → **それまでの依頼文も一緒に送る。画面で目的を直して判定し直せる**（設計書に反映）
- 研究リポジトリにはデータセットやモデルの重みが置かれがちで、スナップショットが重く、`.git` が膨らむ → **1MB を超えるファイルを除く**（設計書に反映）
- localhost の受け取り箱は、ブラウザで開いたほかのサイトからも叩けてしまい、勝手に判定（費用）を走らせられる → **合言葉、`Origin` と `Host` の確認**（設計書に反映）
- 会話記録の形式は公開された仕様ではなく、変わる恐れがある → **読めなくてもエラーなしで判定を続ける**（設計書に反映）
- localStorage（5MB ほど）があふれる → **保存するエラー出力を短く切る**（設計書に反映）
- 依頼文やエラー出力に API キーが混ざる → **キーらしい文字列を伏せ字にする**（設計書に反映）
- 通知が多すぎる、Esc で中断した回の取りこぼし、同時セッションの混ざり、エラーの雑音と取りこぼし、研究テーマとのひも付けの例外、デモモードとの関係、Windows → 設計書の未決事項に残した

## フックが動くタイミングの問題点

- `Stop` は学生の依頼がなくても動くことがあり（裏で動かした学習の終了を受けた再開など）、同じ変更を二重に送る → **送ったらスナップショットを更新する**（設計書に反映）
- Esc での中断や Claude Code が落ちたときは `Stop` が動かず、その回の変更を取りこぼす → **次の依頼のときに、閉じていない前の依頼の分を先に送る**（設計書に反映）
- アプリが止まっていると、送った変更が消える → **貯めて次に送り直す**（設計書に反映）
- 実験の出力（ログ、CSV、グラフ、チェックポイント）が AI の変更として判定される → **拡張子で見分け、ファイル名だけ送る**（設計書に反映）
- AI が作業中に pull やブランチの切り替えをすると、ほかの人の変更が混ざる → **HEAD の動きを見て、判定結果に注意を出す**（設計書に反映）
- スラッシュコマンドが作業の目的になる → **`/` で始まる依頼は目的の履歴に入れない**（設計書に反映）
- 返事が終わるたびに判定されるので作業の途中でも判定される、作業中に追加で送ったメッセージ、会話の切り替えで履歴が切れる、学生や自動整形の変更が混ざる → 設計書の未決事項に残した

## 目的からそれていないかの確認（本物で試したあと）

- フックは、テーマ決めで残っていた「エラー内容をどこから得るか」に答えるもので、本来の目的（AI が黙って対処した問題を、エラー内容と対処方法として残す）の中心に効いている
- 一方で、依頼文をそのまま作業の目的にするので、学生が立ち止まって目的を書く場面がなくなり、⑧（すぐ実装してしまう）への効き目は弱まる
- **決めたこと：今は、学生が目的を書き直したり確かめたりする場面は設けない。** 依頼文をそのまま作業の目的にする。必要になれば、判定結果の画面の「作業の目的を直して判定し直す」で直せる
