## 今回の問い

研究の「調査 → 選定 → 実装」のような流れと、その中で分かれていくタスクを、1枚で確認できるようにしたい。どんな形で、何から作り、どう更新するか。

## 出たアイデア・意見

- アプリの機能として作る。悩み⑩（研究の工程のどこにいるか分からない）と⑦（方針を見失う）に効く。設計書ではグループB（F-11）の範囲だった
- 見た目の候補：3列のレーンとカード（Tailwind だけで作れる）／ノードグラフ（React Flow など）／路線図ふう。レーンとカードにした
- 不採用の枝を理由と一緒に残すと、先生に「なぜその手法？」と聞かれたときの答えになる
- 隠れた問題が研究の前提を変えるときは、実装から選定へ「逆向きの矢印」を引く。汎用のツールにない、研究ならではの見せ場
- 作り方の候補：全部手で登録／AI が下書きして人が確定／全部自動。目的まで AI に書かせると③を繰り返すおそれがあるので、印（AI作成・未確認）と出典を付け、人が直せるようにする
- research-workspace（壁打ち・spec・実験記録・MTG 記録・todo をまとめた GitHub リポジトリ）は、frontmatter でファイル同士がつながっている（spec の `source_brainstorm`・`implementation_verification`・`implementation_reference_commit`、実験記録の `spec`・`base_commit` など）。枝の骨格は AI なしでたどれる。AI にはまとめ方・目的の要約・状態の推測・不採用の抜き出しだけを任せる
- どの spec にも出てこないコミットは「記録のない実装」として目立たせる（⑧のサイン）
- 費用：GitHub API は無料。Claude API は生成が1回数十円〜、取り込みごとの更新が1回十数円〜の見込み。索引をプログラムで作り、変わったファイルだけ送れば下げられる

## 却下した案とその理由

- **タスク＝マイルストーン、サブタスク＝個々の検証（レーンをまたぐ行）**：レーンごとにタスクとサブタスクがある形にしたいので、マイルストーンはレーンをまたぐラベルにした
- **マイルストーンは全レーンにまたがる**：必須ではない。調査だけ、報告だけのマイルストーンもあり、付かないタスクもある
- **提案を1件ずつ承認する形（場面3）**：「AI が作り、人が後から直す」方針に合わせ、自動で反映して取り消せる形にした
- **`code-analysis/` をマップに使う**：工程の記録ではなくコードの説明書なので、いったん使わない

## 決まったこと

- 形：列がレーン（初期値は調査・選定・実装・検証・報告。増減できる）。レーンごとにタスク（カード）とサブタスク（行）。タスク同士のつながりは矢印（flow / impact）
- 各タスク・サブタスクに目的を持たせ、選ぶと研究の問いまでの「目的のつながり」が見える
- AI が research-workspace と実装リポジトリ（別のリポジトリ）を横断して読み、目的も含めて全部作る。人が後から直す
- 却下した提案（人が消したもの）は覚えておき、AI が再び足さない。戻せる
- 場面1（生成）・場面2（修正）・場面3（取り込みごとの自動更新）を作る
- 変更を取り込むたびに自動で更新する
- research-workspace に送ってはいけない内容は含まれていない
- 研究テーマの登録画面に、ワークスペースのリポジトリとプロジェクト名の入力欄を足す（実装リポジトリは spec の frontmatter から埋める）
- タスクは各レーンの作業の単位。マイルストーンはタスクに付けるラベル
- 状態は内部5種類（todo / doing / waiting / done / rejected）で、画面ではレーンの言葉（比較中、承認済み、実行の許可待ちなど）で出す。結果は状態と分ける。決め方は 手動 ＞ 記録 ＞ AI推測。不採用には理由が必須
- デモ用に小さなワークスペースを作る（題材はデモモードと同じ健診データの疾患分類）。まずデモモードで動かす
- 作業はブランチ `feature/workflow-map` で行う
